# 领域建模（Domain Modeling）

在设计的**同时主动**建立并打磨这个项目的领域模型。

这是一门**主动的**功夫：质疑用词、造边界场景去压它、并且在术语和决定**一成形就写下来**。

> （只是**读** `CONTEXT.md` 查词**不算**这个技能 —— 那是任何技能都该有的一行习惯。
> 这个技能用在你要**改变**模型的时候，不只是消费它。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录有 `CONTEXT-MAP.md`，说明这个仓库有**多个**上下文。那张图指向每一个住在哪：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 这个上下文自己的决定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

**按需创建文件**：有东西要写的时候才建。

- 没有 `CONTEXT.md` → 第一个术语定下来时创建一个；
- 没有 `docs/adr/` → 需要第一条 ADR 时创建。

## 会话中怎么做

### 拿术语表去对质

用户用的词与 `CONTEXT.md` 里既有的说法**冲突**时，**当场指出来**：

> 「你的术语表里 'cancellation' 指的是 X，但你这里似乎是 Y 的意思。到底是哪个？」

### 把含糊的说法磨利

用户用了模糊或一词多义的词时，**提出一个精确的规范术语**：

> 「你说 'account' —— 你指的是 Customer 还是 User？这是两个不同的东西。」

### 用具体场景去压

讨论领域关系时，**用具体场景压力测试它**。主动造出能戳到边界情况的场景，
逼用户把概念之间的界线说清楚。

### 与代码交叉核对

用户说某件事是怎么工作的时候，**去看代码是不是也这么说**。发现矛盾就摆出来：

> 「你的代码是把整个 Order 取消掉，但你刚说可以部分取消。哪个是对的？」

### 就地更新 CONTEXT.md

一个术语定下来的那一刻，**当场**更新 `CONTEXT.md`。**不要攒着批量写** ——
它们在发生的当下最清楚，事后补写会丢掉当时的理由。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 里**不该有任何实现细节**。不要把它当规格说明、草稿纸、
或存放实现决定的地方。**它是一份术语表，仅此而已。**

### 克制地提议 ADR

**只有下面三条同时成立**，才提议写一条 ADR：

1. **难以回退** —— 以后改主意的代价是实打实的；
2. **脱离上下文会让人意外** —— 将来的读者会问「他们当年为什么这么干？」；
3. **是真实取舍的结果** —— 确实存在别的选项，而你出于具体理由选了这一个。

**缺任何一条就跳过这条 ADR。** 格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。

> 换个说法：容易回退的决定不用记（你直接回退就行了）；不让人意外的不用记
>（没人会问为什么）；没有真实备选的也不用记（除了「我们做了显而易见的事」没别的可写）。
