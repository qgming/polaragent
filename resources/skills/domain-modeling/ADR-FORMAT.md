# ADR 格式

ADR 放在 `docs/adr/` 下，用连续编号：`0001-slug.md`、`0002-slug.md`……

`docs/adr/` 目录**按需创建**：需要第一条 ADR 时才建。

## 模板

```md
# {决定的简短标题}

{一到三句：背景是什么、我们决定了什么、为什么。}
```

**就这样。** 一条 ADR 可以只有一个段落。

价值在于记录下**做过这个决定**以及**为什么**，而不在于把章节填满。

## 可选章节

只在确实有价值时才加。**多数 ADR 用不上。**

- **Status frontmatter**（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：
  决定会被重新翻出来讨论时有用；
- **Considered Options**：只有当被否掉的备选值得记住时才写；
- **Consequences**：只有当有不明显的下游影响需要点明时才写。

## 编号

扫一遍 `docs/adr/`，取现有最大编号加一。

## 什么时候提议写 ADR

下面三条**必须同时成立**：

1. **难以回退**：以后改主意的代价是实打实的；
2. **脱离上下文会让人意外**：将来的读者看着代码会想「他们当年到底为什么这么干？」；
3. **是真实取舍的结果**：确实存在别的选项，而你出于具体理由选了这一个。

容易回退的**跳过** —— 你直接回退就行了。不让人意外的**跳过** —— 没人会问为什么。
没有真实备选的**跳过** —— 除了「我们做了显而易见的事」没别的可写。

### 什么算数

- **架构形态。** 「我们用 monorepo。」「写模型是事件溯源的，读模型投影进 Postgres。」
- **上下文之间的集成方式。** 「Ordering 与 Billing 通过领域事件通信，不用同步 HTTP。」
- **带锁定效应的技术选型。** 数据库、消息总线、认证服务商、部署目标。
  **不是每个库都要记** —— 只记那些换掉要花一个季度的。
- **边界与范围决定。** 「Customer 数据归 Customer 上下文所有，其他上下文只按 ID 引用它。」
  **明确说出的「不」与「是」同样有价值。**
- **对显而易见的路径的刻意偏离。** 「我们用裸 SQL 而不是 ORM，因为 X。」
  凡是**合理读者会假设成相反做法**的地方都要记 —— 这能拦住下一个工程师
  去「修好」一个本来就是刻意为之的东西。
- **代码里看不见的约束。** 「因为合规要求我们不能用 AWS。」
  「因为合作方的 API 约定，响应时间必须低于 200ms。」
- **否掉某个方案的理由不显然时。** 如果你考虑过 GraphQL、出于微妙的原因选了 REST，
  记下来 —— 否则六个月后会有人再提一次 GraphQL。
