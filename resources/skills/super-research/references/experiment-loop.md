# 模式：实验循环（Experiment loop）

当用户想通过改代码来迭代改进某个可度量的结果时使用 ——「优化」「调参」「跑一整晚实验」「把这个指标爬上去」，任何「仓库里的代码 + 一个数字」的目标。

## 契约字段

开始前先确立以下六项。尽可能从仓库里推断，剩下的用一轮对话确认。

1. **指标（Metric）**：一个数字，一个方向。例如 `val_bpb`（越低越好）、tokens/sec（越高越好）、测试通过率（越高越好）。如果用户抛出多个目标，让他挑出一个**主**指标 —— 多目标循环会卡住，因为「保留还是回滚」变得含糊。次要量（内存、墙钟时间）记为被记录的软约束。
2. **运行命令**：一条能端到端跑完一次实验并打印指标的 shell 命令，例如 `uv run train.py`。同时确定指标怎么提取（例如 `grep "^val_bpb:" run.log`）。
3. **单次实验预算**：固定的墙钟预算能让每次实验彼此可比，无论改了什么（模型规模、batch、算法）。如果这次运行不会自我限时，就约定一个超时。目标 ≤10 分钟/次；超过预算约 2× 的运行直接杀掉。
4. **可改文件 vs 冻结文件**：最理想是只有**一个**可改文件（diff 才好审）。评测/指标代码**永远冻结** —— 会改自己裁判的智能体产出的数字毫无意义。数据处理和依赖清单默认冻结。除非用户明确允许，不引入新的依赖包。
5. **停止条件**：默认是「循环到人类打断为止」。用户可以指定 N 次迭代或时间上限 —— 严格照办。
6. **分支**：新建 `research/<tag>`（tag 取今天日期，例如 `research/jul7`）。该分支必须原本不存在。所有实验提交都落在这里；master 保持不动。

## 基线

第一次运行永远是未经修改的代码。没有例外 —— 没有基线，「改进了」就毫无意义；而且在你还分不清崩溃是自己想法导致之前，基线先验证了这套测量装置本身是能跑通的。

创建 `results.tsv`（tab 分隔），用下面的表头，把基线记为第 1 行：

```
commit	metric	resource	status	description
a1b2c3d	0.997900	44.0	keep	baseline
```

- **commit** —— 短 git hash（7 位）。崩溃那一行填的是崩溃改动被回滚之前的那个 commit。
- **metric** —— 数字。崩溃填 `0`。
- **resource** —— 一个值得跟踪的次要数字（峰值内存 GB、墙钟时间等）。崩溃填 `0`。
- **status** —— `keep` / `discard` / `crash`。
- **description** —— 本次实验假设的简短纯文本描述。

`results.tsv` 不要纳入 git 跟踪。

## 循环

永远循环（或直到停止条件满足）：

1. 记下当前分支/commit —— 这是你的回退点。
2. 形成**一个**假设并修改可改文件。一次实验只验证一个想法：如果你同时改了三处而指标动了，你学不到到底是哪一处起的作用。
3. `git commit` 这次改动（commit message = 这个假设）。
4. 运行：`<run command> > run.log 2>&1`。**一定要重定向** —— 训练输出会淹没你的上下文，把后面五十次实验所需的信号淹掉。
5. 从 `run.log` 里提取指标。
6. 如果提取结果为空，说明这次运行崩了。`tail -n 50 run.log` 看 traceback。低级 bug（拼写错误、漏了 import、shape 不匹配）—— 修好重跑。想法本身根本行不通 —— 记 `crash`，回滚，继续下一个。同一个想法修几次还不行就放弃。
7. 把这一行追加到 `results.tsv`。
8. **保留还是回滚**：指标变好 → 保留这个 commit，前进。持平或更差 → `git reset --hard` 回到回退点。打平的情况判给更简单的代码。
9. 回到第 1 步。

## 判断准则

**简单性优先。** 其他条件相同时，更简单的胜。为了 0.001 的提升加上 20 行 hack 代码，通常不值。**删掉**代码还能打平，那是明确的胜利。

**资源约束是软的。** 为了真实收益，内存/成本涨一点可以接受，但别让它悄悄爆掉。

**没想法了 → 更用力地想，不要停。** 重读范围内的文件找新角度。把之前几次差一点的想法组合起来（两个单独看都没效果的改动，有时能叠加生效）。换不同的幅度重访被丢弃的想法。当增量式改动进入平台期后，试试更激进的结构性改动。允许回退分支，但应该极为罕见。

**当井真的干了 —— 去挖文献。** 如果连续几次实验都聚集在同一个失败模式上，把它当作「你的局部想法用完了」的信号，而不是「指标已经最优」。用共享工具箱把已发表工作里的做法引进来：

```bash
node scripts/paper_search.mjs "<technique> improve <metric>" --sources arxiv,s2 --limit 15 --out papers.json
node scripts/fetch_paper.mjs <arxiv_id> --out paper.txt
```

读摘要（是摘要，不是二手总结），把其中最有可测性的想法拉进下一个假设。把论文 id 记进 `description` 列，这样复核者能把一次实验追回到它的灵感来源。别让这件事变成完整的调研 —— 循环才是主职工作；这是花 15 分钟逃离平台期，不是切换模式。

## 最终报告

见 SKILL.md 的「Reporting」章节。本模式特有的补充：

- **基线指标 vs 最佳指标**，以及两者之差。
- **实验次数**（保留 / 丢弃 / 崩溃各多少）。
- 指向 `results.tsv` 和 `research/<tag>` 分支。
