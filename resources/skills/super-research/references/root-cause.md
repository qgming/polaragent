# 模式：根因排查（Root-cause investigation / 根因排查）

当用户报告一个**坏掉的观察现象、想知道为什么**时使用 —— 回归（「以前是好的」）、间歇性失败（「flaky，大约 20 次里 1 次」）、性能退化（「从周五起慢了 2 倍」）、可疑指标（「转化率一夜之间掉了 8%」）、神秘行为（「只在生产环境失败」）。触发语包括「为什么 X 坏了」「排查根因」「debug 这个回归」「排查」「定位」「复盘」「找出测试为什么 flaky」。

本模式要防范的失败模式：**停在第一个听起来合理的解释上。** 几乎每个回归都有多个相关因素；你找到的第一个很少就是原因。根因需要一次**演示** —— 有能力通过只动**一个**东西来把症状打开和关掉。

## 契约字段

1. **症状**：对「坏了什么」的清晰、可复现的陈述。要具体到例子 —— 命令 / 输入 / URL / 测试名 / 指标阈值。如果用户说「它很慢」，谈判成「端点 /X 在载荷 P 上 p95 延迟 > 800ms（两周前约 150ms）」。模糊的症状只会产出一场模糊的调查。
2. **复现方式**：一条命令或脚本，能按需复现该症状。如果是 flaky，注明复现率（「约 20 次里 1 次」）。如果完全复现不出来，循环的第一阶段就是**复现**而不是根因 —— 在契约里说清楚，不要跳过去。
3. **已知良好参照**：一个**没有**观察到该症状的 commit、环境、配置或时间窗。正是它让二分查找成为可能。如果不知道，谈判出一个 —— 用户往往知道「周一还好好的」或「staging 上是好的」。
4. **爆炸半径规则**：调查期间你被允许动什么？生产环境读操作通常没问题；生产写操作和破坏性操作，没有明确签字就不行。把这些写进契约，你就不用中途再问。
5. **停止判据**：默认是「原因已被定位，并通过一次针对性修复或针对性重新引入得到演示」。较弱的「这是排名前三的嫌疑，按可能性排序」只有在契约明确允许时才可接受（例如在你可访问的环境里无法复现）。
6. **工作目录**：专用文件夹 `investigation/<tag>/` —— 复现脚本、日志、证据、任何补丁。

## 基线 —— 把症状量化

你的基线不是「我改动之前的代码」，而是**被变得可测量的症状**。在任何假设之前：

- 把复现跑 N 次（flaky 的情况跑 10–30 次）并记录：通过/失败率、耗时分布、逐字的错误信息。存到 `baseline.md`。这就是你要推动的东西。
- 把同一个复现在已知良好参照上跑一遍，记录同样的数字。两者之差，就是你要解释的效应的**大小**。
- 任何不能预测出「方向正确、量级大致相当」的变化的假设，都是干扰项。之后，这个基线也是你验证修复的方式。

## 假设日志

`hypotheses.tsv`（tab 分隔），每个考虑过的假设一行 —— 包括你很早就排除掉的：

```
id	hypothesis	prediction	test	result	status	notes
H01	env var X was unset in prod after Fri deploy	symptom reproduces locally when X is unset	unset X; run repro 20×	20/20 pass — X does NOT reproduce it	ruled-out	
H02	commit abc123 (retry-loop change) is the trigger	git bisect between last-good and HEAD lands on it	bisect 12 commits, ~4 steps	landed on abc123	suspect	
H03	abc123's off-by-one causes double-close on retry	reverting abc123 alone fixes the symptom AND replaying the diff onto known-good REINTRODUCES the symptom	revert + rerun 30×; cherry-pick onto old + rerun 30×	revert: 30/30 pass. cherry-pick: 28/30 fail (matches baseline rate)	confirmed	both directions match — this is the cause
H04	load balancer stickiness change same day	drops out under H03 if we can reintroduce symptom on isolated node	—	—	unexplored	deprioritized after H03 confirmed
```

- **prediction** —— 在跑测试**之前**，如果假设为真你预期看到什么。这一列要在 result 列**之前**填。如果你只能在看到结果之后才说得出预测，那你是在做模式匹配，不是在做检验。
- **status** —— `unexplored` / `testing` / `ruled-out` / `suspect` / `confirmed`。只有当因果检验的**两个方向**都一致时，`suspect` 才能升级为 `confirmed`。

**被排除的假设也要记。** 它们证明了你是真的试图证伪自己最中意的理论，而不只是在确认它。一份只有一条记录、状态是 confirmed 的日志不是调查，是把一个猜测写下来而已。

## 循环

循环直到某个假设被 `confirmed`，或者停止判据以其他方式满足：

1. **如果复现是 flaky 的或者根本复现不出来，先把这件事解决。** 在不可靠的基线上做调查是愚蠢的 —— 你根本分不清你的干预有没有生效。调整种子、隔离失败用例、增加迭代次数，直到复现率稳定到足以把信号和噪声区分开。
2. 挑下一个信息量最大的假设 —— 那个「无论结果如何，都能最快切分剩余原因空间」的假设。
   - **优先二分查找，而不是猜。** 如果在已知良好和 HEAD 之间存在一个坏的 commit，`git bisect` 用 log₂(N) 步就能找到它，且不依赖你有多聪明。在做复杂的理论推演之前先做这个。
   - **优先做环境对比。** 对「这里能跑、那里失败」的问题，系统地对比环境变量、版本、配置、硬件、时序 —— 这两个环境就是一个天然实验的两个条件。
3. 在跑测试**之前**写下预测。然后才运行。
4. 记录结果。更新状态。
5. **绝不停在 `suspect`。** 只有当因果检验在两个方向上都通过，假设才算确认：(a) 去掉嫌疑因素能消除症状，**且** (b) 重新引入嫌疑因素（或它的关键部分）能让症状以基线速率回来。单方向可能因为混杂因素而「通过」。两个方向同时碰巧一致的情况极为罕见。
6. 继续循环。

## 判断准则

**相关不是因，双向反转才是因。** 二分找到的 commit、改动的环境变量、新部署的依赖 —— 全都是嫌疑，不是结论。在你展示出「去掉它 → 症状消失，放回去 → 症状回来」之前，你手里只有线索，没有根因。这个区别就是真正的调试和自信地瞎比划之间的差别。

**警惕那种「让它能跑就行」的修复。** 撒一层 `try/except`、加一次重试、把超时调大 —— 这些都能在没有触及原因的情况下让症状安静下来。如果你能说清的机制预测不出你实际观察到的那个症状，就继续查。「现在能跑了」是第二容易骗到自己的方式，仅次于「我在 diff 里发现了可疑的东西」。

**证伪优先于证明。** 问自己「什么样的测试结果能证明我错了？」—— 如果你说不出来，这个假设还不够科学，它只是个故事。把测试设计成**证伪**你最看好的候选，而不是再确认它一遍。

**促成因素 vs 根因。** 有时诚实的答案是「A 是触发器，但只是因为 B 早就在那儿了」—— 例如一个一直存在的竞态，被某次调度器改动暴露出来。两个都要报告。只说触发器，就留下了漏洞；只说潜伏的 bug，读者会疑惑为什么是现在爆发。

**确认不了的时候，就说你把它缩小到了什么范围。** 一场以「在 {A, B} 中确认，排除了 {C, D, E, F}」结尾的调查，远比以「一个包装成答案的猜测」结尾的调查有用得多。

## 最终报告

见 SKILL.md 的「Reporting」。模式专属正文：

- **根因** —— 一句话点出原因，并带上演示过的双向反转（「回滚 X 修复；重新应用 X 又坏了」）。
- **症状 → 原因链条** —— 机制，一段话。包括促成因素。
- **证据** —— 指向 `hypotheses.tsv`，以及承载这次演示的具体 H-ID。
- **已排除项** —— 你排除掉的主要替代解释，以及排除它们的测试。这是把「诊断」和「猜测」区分开的东西。
- **修复 / 缓解** —— 针对根因的最小改动（如果在范围内），以及任何值得提工单的潜伏 bug 后续项。
- **往哪里看**：`hypotheses.tsv`、`baseline.md`、复现脚本、`investigation/<tag>/`。
