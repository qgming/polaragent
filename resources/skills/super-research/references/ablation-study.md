# 模式：消融实验（Ablation study / 消融实验）

当用户想**把某个结果归因到具体组件**时使用 ——「X 里哪些部分才是真正重要的」「组件 Y 到底有没有贡献」「对这条流水线做消融」「消融实验」「归因研究」「这个特性在扛活吗」。目标是**理解**，不是改进：你在拆解一个能工作的系统，搞清楚哪些零件在承重。

本模式要防范的失败模式有两个：(1) 仅凭一次噪声很大、碰巧超过噪声底的运行就宣称某个组件「重要」；(2) 找到最大的效应就停下，剩下的悄悄不测了 —— 这会产出一份看起来斩钉截铁、实则建立在残缺矩阵上的归因。

消融和实验循环的区别在于：那里你保留能改善指标的改动、回滚其余的。这里，**每一次**移除你都要保留并记录，无论指标是改善、持平还是变差 —— 这正是本模式的全部意义。

## 契约字段

1. **参照配置**：你正在归因的那个确切的「完整」系统。冻结且可重复 —— 一个 commit、一份配置、一组种子。每一次消融都是相对它测量的。
2. **组件**：一份显式枚举的可消融单元清单 —— 特性、层、损失项、流水线阶段、提示词段落、工具调用、正则项。如果某个组件有天然的细分（例如「attention」= QKV + softmax + 输出投影），在契约阶段就决定是整体消融还是分部件消融。看到结果之后再做子部件决策，就是归因版的 p-hacking。
3. **消融操作**：每个组件如何被「移除」—— 置零、替换为单位映射、替换为平凡基线（随机 / 均值 / no-op），或硬删除。**这个选择很重要，而且必须在所有组件上保持一致** —— 混用「置零」和「替换为随机」会产出不可比较的 delta。选定一种并坚持，或者对每个组件都跑所有方法（很少值得）。
4. **主指标**：形状同实验循环 —— 一个数字、一个方向 —— 因为 delta 之间需要可比。次要指标（内存、延迟、成本）记录在案。
5. **公平预算**：每次消融运行使用相同的墙钟 / 迭代 / 数据预算。相同的评测集。相同的种子 —— 或者，如果种子敏感性重要，就为每次消融使用相同的**种子集合**。
6. **重复次数**：在开始消融**之前**，参照配置至少跑 3 次以建立噪声底。然后每次消融至少 2 个种子（若噪声底与你预期效应量级相当，就更多）。
7. **工作目录**：专用文件夹 `ablation/<tag>/` —— 测量装置、消融日志、每次运行的输出。

## 基线 —— 测量噪声底

在任何消融之前，用不同种子把参照配置跑 ≥3 次。这给你：

- **参照均值与标准差** ——「什么都不改」时的指标是多少，以及它有多大波动。
- **噪声底** —— 可能是一个真实效应而非运行间方差的**最小**指标 delta。任何 delta 落在这一带内的消融，属于「无可测量的贡献」，而不是「没有贡献」（两者有区别 —— 用你当前的实验设置分辨不出来）。

把这些记为消融日志的头几行。你之后的一切声称，都是相对它们测量的。

## 消融日志

`ablation.tsv`（tab 分隔），每个（配置 × 种子）一行：

```
config	component_removed	seed	metric	resource	status	delta_vs_ref	notes
reference	—	0	0.812	1.2	done	0.000	
reference	—	1	0.809	1.2	done	-0.003	
reference	—	2	0.815	1.2	done	+0.003	noise floor: ±0.003 (±1σ)
ablate_attention	attention	0	0.740	1.1	done	-0.072	well outside noise band — component carries load
ablate_dropout	dropout	0	0.813	1.2	done	+0.001	inside noise band — no measurable contribution
ablate_dropout	dropout	1	0.808	1.2	done	-0.004	inside noise band
ablate_layernorm	layernorm	0	0	0	crash	NaN	training diverges without layernorm — critical, not merely helpful
ablate_reg_term	reg_term	0	0.816	1.2	done	+0.004	possibly helpful to remove — repeat with more seeds
```

- **delta_vs_ref** —— 指标减去参照均值，方向按指标本身（若越高越好，正 = 更好；负 = 更差）。在汇总步骤填写，而不是运行时填。
- **崩溃也是归因。** 一个组件被移除后系统灾难性失败，说明它是**承重的**，而这属于最强的归因结果之一。不要悄悄用「修复」重试 —— 记录崩溃，然后继续。

`ablation.tsv` 不要纳入 git 跟踪。

## 循环

1. 建立噪声底（见上面的基线）。记录参照运行。
2. 对冻结清单里的每个组件，在完全相同的条件下、以 ≥2 个种子跑消融。把运行输出重定向到文件；机械地提取指标。
3. 记录每一次运行 —— 包括崩溃和发散的训练。
4. **把种子在各消融之间交错安排**（ablate_A seed 0、ablate_B seed 0、ablate_C seed 0、ablate_A seed 1、…）。把每个消融连续跑成一整块，会让随时间变化的噪声与顺序相关。
5. 矩阵跑完后，计算每次消融的均值 delta ± 标准差。
6. **相对噪声底对每个组件分类**：
   - `|Δ|` 落在噪声带内 → **无可测量的贡献**（在给定预算/种子下）。
   - `Δ` 比参照差且超出噪声 → **承重**（以指标单位给出幅度）。
   - `Δ` 比参照好且超出噪声 → **有害** —— 该组件是移除的候选；在建议移除之前先调查（意外的正效应有时意味着消融本身有 bug）。
   - 崩溃 / 发散 → **关键（critical）** —— 该组件是系统能运行的必要条件，而不只是达到该指标的必要条件。
7. **不要提前停。** 即使已经找到一个大效应，也要把矩阵剩下的部分跑完。选择性消融正是系统积累「 cargo cult 组件」的方式：每个人「都知道」X 和 Y 重要（因为当初只跑了这几个消融），而没人注意到 Z 已经六个月什么也没做了。

## 判断准则

**delta 只有相对噪声底才有意义。** 报告每个 delta 时都要附上与参照标准差的比较。同样是声称 0.02 的改进，噪声底是 0.005 还是 0.03，含义天差地别。如果两者量级相当，答案就是「我们分辨不出来」，而不是「效应很小」。

**警惕交互作用。** 留一法（leave-one-out）消融归因的是某组件**在其他人都在场时**的边际效应。它不会告诉你哪些组件只有**一起**才起作用。如果用户需要理解交互（A 是不是只在 B 存在时才有帮助？），那是第二阶段的 2×2 或 2^k 网格，不该偷偷塞进 LOO 矩阵里。

**「无可测量的贡献」的组件也要报告。** 它们往往就是可行动的发现 —— 删除、简化或降低算力的候选。一份只展示胜利的研究读起来像在给参照配置辩护；一份展示零结果的研究读起来像一次审计。

**崩溃值得在报告里单独占一行。** 「组件 X 被移除后会导致发散」是一条关键的文档记录，也是比「移除 X 让指标掉了 5 个点」更强的归因形式。要按这个分量对待它。

**当消融反而改善了指标时，别庆祝 —— 去调查。** 消融下指标变好，通常意味着要么 (a) 该组件一直在起反作用，值得用一次针对性研究确认，要么 (b) 这次消融顺带改动了别的东西。在建议 (a) 之前先排除 (b)。

## 最终报告

见 SKILL.md 的「Reporting」。模式专属正文：

- **归因表** —— 每个组件一行，含均值 delta ± 标准差、分类（承重 / 无可测量贡献 / 有害 / 关键）和一句话解读。
- **参照与噪声底** —— 一切测量所相对的那些数字，要醒目。没有它们，这张表无法解读。
- **意外发现** —— 结果比预期更不重要的组件，或反而改善了指标的消融，附后续说明。
- **交互作用方面的局限** —— LOO 的局限，以及用户在据结果行动之前应当知道的任何交互。
- **往哪里看**：`ablation.tsv`、测量装置脚本、`ablation/<tag>/` 里的每次运行日志。
