# 模式：复现论文（Paper reproduction / 复现论文）

当用户递给你一篇论文（arXiv id、DOI、PDF 或 URL）并要求一份能跑的代码实现时使用 ——「复现这篇论文」「paper to code」「实现这个方法」「复现 X 的主表」。

本模式要防范的失败模式：产出一个**看起来**像该论文实现、却悄悄偏离了论文的仓库 —— 硬编码的数字、凭想象补上的未言明超参数，或者一个从未真正重跑过论文实验的「复现」。每一处含糊都必须是**被记录下来的决定**，而不是看不见的猜测。每一个报告出来的数字都必须来自你代码的**实际运行**，而不是来自论文。

## 契约字段

1. **论文**：arXiv id / DOI / URL。还有：是否存在官方参考实现？（在决定从零复现之前，先查 GitHub —— 主会话用 `browser_open` + `browser_snapshot`，子智能体用 `bash` + `curl`；用户可能只是想让你跑他们的代码。）
2. **范围**：要复现哪些实验。几乎从来不是「全部」。通常是主结果表 + 用户关心的一到两个消融。一次命中了数字的**有范围**复现，抵得上十次开了头就废弃的完整复现。
3. **算力现实性**：如果论文的完整训练在这个环境里不可行（多节点、几周 TPU 等），事先约定一条**缩比验证路径**：更小的模型、数据子集、更少的步数。最终报告要说明哪些是完整的、哪些是缩比的 —— 绝不悄悄假装。
4. **交付物**：一个 `paper/<tag>/` 目录，含 `plan.md`、`analysis.md`、代码仓库、`config.yaml`、`results.tsv` 和 `REPORT.md`。
5. **冻结输入**：论文正文就是规格说明书。如果存在官方仓库且与论文矛盾，在日志里标出这处分歧 —— **不要**在未记录选择的情况下悄悄跟随任何一方。
6. **停止条件**：数字落在论文报告值的约定容差内，或者存在一个有据可查、且有合理解释的差距（算力更少、未言明的超参数、数据版本不同），或者算力预算耗尽。

## 基线 —— 把论文产物落到磁盘上

在写第一行实现代码之前，先产出这些产物。它们是你的基线；如果产不出来，说明复现条件还不具备。

```bash
# LaTeX 源码 —— 首选：精确的公式、表格、超参数
node scripts/fetch_paper.mjs <arxiv_id_or_url> --latex --out-dir paper/<tag>/src/
# 兜底（有些电子预印本只有 PDF）：经 ar5iv 拿到可读文本
node scripts/fetch_paper.mjs <arxiv_id_or_url> --out paper/<tag>/paper.txt
```

然后写：

- **`plan.md`** —— 用你自己的话写的方法概述（附章节/公式编号）、范围决策（做哪些实验）、仓库骨架（文件树，每个文件一句话职责）、依赖图。
- **`analysis.md`** —— 对骨架里的每个文件，在写任何代码之前先写清：输入/输出、它实现论文里的哪些公式、边界情况，以及**论文中每一处含糊的地方**。这份含糊清单就是复现的风险登记册。
- **`config.yaml`** —— 论文提到的每一个超参数，附上论文中的取值和章节引用。论文未言明的标为 `# [uncertain: not specified in paper, using common default of X]`。

如果论文经不起与 `analysis.md` 的接触 —— 含糊清单长到大多数数字都只能靠猜 —— 那就停下并报告这一点，而不是继续往下做。

## 复现日志

`results.tsv`（tab 分隔），任何实验的每一次尝试运行记一行。schema 同实验循环，外加一个 `target` 列：

```
commit	experiment	target	metric	resource	status	description
a1b2c3d	main_table_row1	0.312	0	0	crash	shape mismatch in attention block — see run.log
b2c3d4e	main_table_row1	0.312	0.415	1.2	discard	fixed shape bug; runs but 30% off paper — investigate
c3d4e5f	main_table_row1	0.312	0.318	1.2	keep	set warmup steps to 500 per §4.2; within tolerance
c3d4e5f	main_table_row2	0.287	0.291	1.3	keep	same config generalizes to row 2
```

- **experiment** —— 这一行针对的是论文里的哪个结果（例如 `main_table_row1`、`ablation_no_dropout`）。
- **target** —— 论文为该实验报告的数字。从论文里一次性填入，之后永不修改。
- **metric / status** —— 同实验循环（`keep` / `discard` / `crash`）。

另有一份 `ambiguities.tsv`（或 `analysis.md` 中的一节）记录每一处含糊的解决方式：论文的哪个位置、含糊点是什么、你选了什么、为什么。这些是复核者会最先读的决定。

## 循环

按依赖顺序实现（依据 `plan.md` 的依赖图）。对每个模块：

1. 记下当前分支/commit —— 回退点。
2. 实现该模块最小可用的版本。一个 commit 一个模块。
3. 单元级冒烟测试：它产出的 shape/类型是下一个模块所期望的吗？是就继续；不是就修。
4. 当模块足够多、能端到端跑通范围内的实验时，运行它：`<run command> > run.log 2>&1`。
5. 机械地提取指标。往 `results.tsv` 追加一行。
6. 与 `target` 比较：
   - 在容差内 → 标记 `keep`，继续下一个实验或消融。
   - 差很远 → 这才是有意思的情况。**不要**针对论文的测试数字去调参（那是对 target 过拟合 —— 一种已知的、会同时骗到自己和用户的做法）。改为：重读 `analysis.md`、重访含糊点、在日志里找某个你用猜测填上的超参数。
   - 崩溃 → `tail -n 50 run.log`；修好，或记一条 dead end。
7. 每一处含糊的解决方式都要在发生时记录下来。

**绝不修改论文。** 论文正文就是规格说明书；如果论文本身有错或自相矛盾，注明它并选一种解决方式 —— 不要为了迎合你的做法去改写论文的说法。

## 判断准则

**完整训练 vs 缩比验证：永远要说清是哪种。** 如果你因为全量数据上跑 10 万步不可行而只在子集上跑了 100 步，报告要在开头就说明。悄悄只用了 1% 算力的「复现」，是靠隐瞒构成的谎言。

**差距是正常的 —— 解释它们。** 复现很少能精确命中论文的数字（算力不同、超参数未言明、数据集版本、框架数值行为）。3% 的差距加上有据可查的合理解释，是有效结果。30% 的差距加一句「差不多够了」，不是。

**不要靠调参把自己调到论文的数字上。** 如果你发现自己在一个个扫超参数、直到某个特定的测试集数字出现，就停下。那是对 target 过拟合，产出的是一个背下了论文表格、而非复现了其方法的仓库。如果用户明确要求做命中目标的扫参，在报告里显著注明。

**配置优先于代码。** 每个超参数都住在 `config.yaml` 里，绝不硬编码在模块中。复核者第一个看的就是配置 —— 把一个未言明的默认值埋在代码深处，恰恰藏起了最要紧的那处含糊。

**官方仓库的分歧是一条发现。** 如果论文说一套、发布的代码做另一套，那就是论文 vs 实现的对立 —— 你必须选一个并记录选了哪个。不要把「代码是这么写的」当作自动高于论文的真理。

## 最终报告

见 SKILL.md 的「Reporting」。模式专属正文：

- **复现小结** —— 一段话：引用的论文、复现的范围、算力路径（完整还是缩比）。
- **数字表** —— `experiment | paper | ours | gap | note`。**这张表就是报告本身**；其余一切都是为它服务的。
- **已解决的含糊点** —— 论文中含糊处的清单，以及每一处是怎么定的。这正是复核者会拿去对照论文正文核验的东西。
- **已知偏离** —— 你在哪里偏离了论文（或官方仓库）、为什么，以及对数字的预期影响。
- **复现命令** —— 那条能从零重新生成数字表的精确 shell 命令。
- **往哪里看**：`plan.md`、`analysis.md`、`config.yaml`、`results.tsv`、`ambiguities.tsv`、代码仓库、`paper/<tag>/`。
