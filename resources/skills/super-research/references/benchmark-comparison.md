# 模式：对比评测（Benchmark comparison / 对比评测）

当用户想要**在 N 个候选之间做选择**时使用 —— 库、模型、算法、提示词、配置 ——「对比 X 和 Y」「这些里哪个最适合我们」「给这些做个 benchmark」「选型」「对比评测」。目标是**选型**，不是改进：你不去爬任何一个候选的坡，而是在完全相同的条件下测量它们全部。

本模式要防范的失败模式：一次不公平的比较 —— 候选跑在不同条件下、调优程度不均、或只在挑出来的个例上评判 —— 然后宣布一个「赢家」，却不谈那些会改变决策的取舍。

## 契约字段

1. **候选**：一份显式、冻结的清单。中途加入候选，只有在**为它把整个矩阵在相同条件下重跑一遍**时才允许 —— 覆盖不全的候选会悄悄让排名失真。如果用户有在用的现役方案（「我们现在用的那个」），把它也作为一个候选纳入；它是最有意义的参照点。
2. **任务矩阵**：每个候选都会跑的那组固定的测试用例 / 工作负载 / 输入。必须在第一次测量运行**之前**定义好。看到结果之后再选用例，就是 benchmark 版的 p-hacking。
3. **指标**：一个决定排名的**主**指标（一个数字、一个方向），加上若干次要指标（延迟、内存、成本、接入复杂度），后者记入日志并用于说明取舍。所有候选都由**同一套**测量装置代码测得 —— 绝不用候选自己上报的数字。
4. **公平预算**：每个候选投入相同的功夫 —— 例如「只用默认配置」或「每个最多调 15 分钟」，以及每个格子固定的重复次数以估计方差。如果某个候选非得特殊处理才能跑起来（适配层、格式转换），允许，但要记录；这本身就是一条关于接入成本的发现。
5. **环境**：锁定版本、硬件、随机种子。记下任何可能在运行之间漂移的东西（热降频、网络、API 限流）。
6. **工作目录**：专用文件夹 `benchmark/<tag>/` —— 测量装置、矩阵日志、每次运行的输出都放那里。

## 基线 —— 先验证测量装置

在任何正式测量之前，先用**一个**候选和**一个**用例给装置做冒烟测试，并肉眼看一下输出。一套坏掉的装置测 60 次，只会产出 60 个自信的错数字。如果存在平凡的参照（no-op、随机猜、现役方案），先跑它 —— 它校准出在你的矩阵上「好」意味着什么。

## 矩阵日志

`matrix.tsv`（tab 分隔），每个（候选 × 用例 × 重复）一行：

```
candidate	case	rep	metric	resource	status	notes
lib_a	case01	1	0.912	1.2	done	
lib_a	case01	2	0.909	1.2	done	
lib_b	case01	1	0.877	0.4	done	
lib_b	case07	1	0	0	error	throws on unicode input — see run logs
lib_c	case07	1	0	0	timeout	killed at 2× budget
```

- **status** —— `done` / `error` / `timeout` / `unsupported`。每个计划中的格子都要有一行；格子为空意味着比较不完整，排名不可信。
- **失败是发现，不是排除项。** 一个在 20% 用例上报错的候选，是关键的决策数据。绝不要为了让某个候选的平均分「干净点」而丢掉它的坏格子 —— 把失败按最坏情况计分，或者单独报告覆盖率，并说明你用的是哪种做法。

## 循环

1. 给测量装置做冒烟测试（见上面的基线）。
2. 跑矩阵。**把重复次数在各候选之间交错安排**（A,B,C,A,B,C…），而不是一个候选跑完一整块 —— 这样随时间变化的噪声（热、网络、缓存）会均匀摊开，而不是偏袒先跑的那个。
3. 每完成一个格子就记录，包括失败。把运行输出重定向到文件；用 grep/脚本提取指标，不要用眼睛。
4. 矩阵跑完后做汇总：主指标上每个候选的均值 ± 标准差，以及按用例和总体的排名。
5. **稳定性检查**：每次去掉一个用例，重新计算排名。如果赢家会因单个用例而翻转，结论就是脆弱的 —— 报告出来，不要藏。
6. 可选的第二阶段（仅在契约允许时）：给每个候选相同的预算做调优，然后重跑矩阵。在日志里把第一阶段和第二阶段的结果清楚分开 —— 把调过和没调的混在一起，是让报告变得没法读的最快方式。

## 判断准则

**不要偏袒你心仪的那个。** benchmark 撒谎最常见的方式就是投入不均：花几小时打磨你预期会赢的候选，其余的用默认配置。预算要相等，并且用机制强制执行。

**「取舍前沿」是有效答案。**「A 快 3 倍，B 准确率高 4 个点，C 是唯一能处理你的 unicode 用例的」往往比硬挤出一个单一赢家更有用。只有当某个候选全面占优、或者用户的优先级让选择显而易见时，才宣布单一赢家。

**警惕矩阵与候选不匹配。** 如果某个候选只在那些对用户真实工作负载而言边缘的用例上输，要说出来。矩阵只是对现实的近似；指出近似的薄弱处。

**先看方差，再下判决。** 如果每个格子的重复显示标准差与候选之间的差距相当，那么下一步需要的是**更多重复**，而不是结论。

## 最终报告

见 SKILL.md 的「Reporting」。模式专属正文：

- **推荐** —— 赢家，或者取舍前沿加一条决策规则（「除非你需要 X，否则选 A」）。
- **排名表** —— 每个候选的主指标均值 ± 标准差、关键次要指标、失败/覆盖率。
- **稳定性** —— 排名在去掉单个用例后是否依然成立？哪里脆弱？
- **接入说明** —— 从日志里取，哪些候选需要特殊处理。
- **往哪里看**：`matrix.tsv`、测量装置脚本、`benchmark/<tag>/` 里的每次运行日志。
