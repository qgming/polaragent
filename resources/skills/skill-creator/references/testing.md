# 测试与迭代

**按技能的受众决定投入的严谨程度**：自己用的技能手工抽查几次就够；
要发给整个团队的，值得写一套脚本化的测试用例。

> **高价值做法**：在一件**难**的任务上反复迭代到智能体成功，
> 再把赢的做法提炼进技能。这比一开始就广泛测试信号快得多。
> 基础跑通了再扩展到多个用例。

## 1. 触发测试

目标：**该加载的时候加载，不该加载的时候不加载。**

像这样列一组用例：

```
应该触发：
- 「帮我建一个新的 ProjectHub 工作区」        （明显）
- 「我要在 ProjectHub 里建个项目」            （换说法）
- 「为 Q4 规划初始化一个 ProjectHub 项目」    （换说法）

不该触发：
- 「旧金山天气怎么样？」
- 「帮我写段 Python 代码」
- 「建个表格」  （除非这个技能就是处理表格的）
```

目标是**相关请求里约 90% 能触发**。

调试方法：直接问智能体「你什么时候会用 [技能名] 这个技能？」——
它会用自己的话把 description 复述回来；**它漏掉的，就是描述里缺的。**

## 2. 功能测试

目标：技能产出正确的结果。

```
用例：建一个带 5 个任务的项目
给定：项目名「Q4 规划」，5 条任务描述
当：  技能执行工作流
则：  项目已创建；5 个任务属性正确；
      任务之间已建立关联；没有 API 报错
```

要覆盖：正常输出、工具 / API 调用成功、错误处理生效、边界情况。

## 3. 与基线对比

目标：**证明这个技能比不用它更好**。同一个任务跑两遍（用 / 不用技能）比较：

```
不用技能：15 轮来回，3 次 API 调用失败，12,000 token
用技能：  2 个澄清问题，0 次 API 调用失败，6,000 token
```

定性检查：用户需要自己追问下一步吗？同一请求跑 3–5 次，产出结构一致吗？
一个没用过的人能第一次就成功吗？

## 迭代信号

技能是**活文档**。留意这些信号：

| 现象 | 诊断 | 修法 |
|---|---|---|
| 该加载时不加载；用户手动调用它 | **触发不足** | 往 description 里补细节、关键词、用户真会说的原话 |
| 不相关的问题也加载；用户把它禁用了 | **触发过度** | 加否定触发（「不要用于…」），收窄范围 |
| 结果不一致、调用失败、用户反复纠正 | **执行问题** | 磨利指令、补错误处理、把散文式校验换成脚本 |
| 响应变慢 / 变差 | **上下文膨胀** | 缩小 SKILL.md，细节挪进 `references/` |

真实会话里冒出边界情况或失败时，**把那段对话带回来，直接把修法写进技能**：
一条明确的指令、一条疑难条目、或一个校验步骤。**这是价值最高的迭代回路。**

## 常见故障

**「找不到 SKILL.md」** —— 文件名不是正好 `SKILL.md`（大小写敏感）。

**「frontmatter 无效」** —— 缺 `---` 分隔，或 YAML 格式坏了（引号没闭合是最常见的原因）。

**「技能名无效」** —— `name` 里有空格或大写；用 kebab-case。

**技能加载了但指令被忽略** —— 指令太长或被埋住了。保持精炼，把关键规则放到最前面
（用 `## 重要` 之类的标题），细节挪进 `references/`。必须通过的校验就**打包成脚本**，
不要指望散文描述。

**技能完全不出现（连索引里都没有）** —— **缺 `description`**。这是唯一会让技能被
**静默丢弃**的情况：文件还在磁盘上，但模型看不到它，而唯一的线索是一行
`description is required` 的 warning。补上 description 即可。

**description 超长（>1024）** —— 技能**仍会装载**，只是多一条 warning。
不致命，但描述该压短（它每轮都占 token）。
