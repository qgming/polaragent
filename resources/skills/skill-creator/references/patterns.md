# 技能结构模式

从真实技能里总结出来的几种成熟做法。**先定框架**：

- **问题优先**：用户描述一个产出（「把项目工作区建起来」）→ 技能负责按正确顺序编排工具；
- **工具优先**：用户已经有工具（一个 MCP server、一个 CLI）→ 技能教它最优的工作流与最佳实践。

多数技能偏向其中一边。知道自己属于哪边，有助于从下面挑一个模式。

## 模式 1：顺序工作流编排

用于用户需要**按特定顺序**走完多步流程的场景。

```markdown
## 工作流：新客户上手

### 第 1 步：建账号
调用工具：`create_customer` —— 参数：name、email、company

### 第 2 步：配支付
调用工具：`setup_payment_method`。等待：支付方式验证通过。

### 第 3 步：建订阅
调用工具：`create_subscription` —— 参数：plan_id、customer_id（来自第 1 步）

### 第 4 步：发欢迎邮件
调用工具：`send_email` —— 模板：welcome_email_template
```

关键手法：**显式的步骤排序**、写明步骤间的依赖、每一阶段都有校验、失败时有回退说明。

## 模式 2：多 MCP 协调

用于流程跨越多个服务的场景。

```markdown
## 阶段 1：设计导出（Figma MCP）
导出素材、生成规格、创建素材清单。

## 阶段 2：素材入库（Drive MCP）
建项目文件夹、上传素材、生成可分享链接。

## 阶段 3：建任务（Linear MCP）
创建开发任务、附上素材链接、指派给工程。

## 阶段 4：通知（Slack MCP）
发出交接摘要，带素材链接与任务引用。
```

关键手法：**阶段划分清晰**、服务之间显式传递数据、推进到下一阶段前先校验、
错误处理集中在一处。

## 模式 3：迭代改进

用于**输出质量会随迭代提升**的场景。

```markdown
## 初稿
取数据 → 生成第一版 → 存到临时文件。

## 质量检查
跑 `scripts/check_report.py`；找出缺章节、格式不一致、数据校验错误。

## 改进循环
逐条处理问题 → 重生成受影响的章节 → 重新校验 →
重复，直到达到质量阈值。

## 定稿
套用最终格式、生成摘要、存最终版本。
```

关键手法：**明确的质量标准**、校验脚本、**一个明确的停止条件**（知道什么时候别再迭代）。

## 模式 4：按上下文选工具

用于**同一件事在不同情况下要用不同工具**的场景。

```markdown
## 决策树
1. 看文件类型与大小
2. 选存储方式：
   - 大文件（>10MB）：云存储 MCP
   - 协作文档：Notion / Docs MCP
   - 代码文件：GitHub MCP
   - 临时文件：本地存储
3. 执行，套用该服务特有的元数据，生成访问链接
4. 告诉用户为什么这么选
```

关键手法：**清晰的判断标准**、有兜底选项、**对选择保持透明**（说清为什么这么选）。

## 模式 5：领域知识内嵌

用于技能**除了工具访问之外还带来专门知识**的场景。

```markdown
## 处理前（合规检查）
取交易详情 → 套用合规规则（制裁名单、司法辖区许可、风险等级）→ 记录判断。

## 处理
若合规通过：带欺诈检查处理支付。
否则：标记待复核，并建一个合规案例。

## 审计留痕
记录全部检查、记下判断、生成审计报告。
```

关键手法：**领域知识写进判断逻辑**、动作之前设合规关卡、完整的文档留痕。

## 组合与可移植

- **智能体可以同时加载多个技能** —— 永远不要假设只有你这一个能力可用；
  适合别处做的时候就交给别的技能（例如「下载下来的文件用 PDF 处理技能去读」）；
- 技能应当在各个界面下表现一致。**环境要求写进正文**（Oint 只解析
  `name` / `description` / `disable-model-invocation`，写别的 frontmatter 字段不会生效），
  不要假设环境一定满足。
