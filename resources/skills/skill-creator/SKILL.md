# 技能创建（Skill Creator）

一个技能就是一个**文件夹**，教智能体如何处理某件具体的事：

```
your-skill-name/
├── SKILL.md       # 必需 —— YAML frontmatter + Markdown 正文
├── scripts/       # 可选 —— 可执行代码
├── references/    # 可选 —— 只在需要时才读的文档
└── assets/        # 可选 —— 模板、字体、图标等产出物要用的素材
```

技能依赖**渐进式披露**：frontmatter 永远在上下文里（所以它决定技能**什么时候**被加载），
正文在相关时加载，被链接的文件只在按需读取时加载。**每一层都尽量小。**

## 工作流：新建一个技能

### 第 1 步：先定下 2–3 个具体用例

动笔之前，和用户确认：

- 用户想达成什么？（要的是**产出**，不是功能点）
- 什么会触发它？**收集用户真会说的原话。**
- 这套流程按顺序需要哪些步骤？
- 需要哪些工具（内置工具、脚本、MCP server）？
- 必须内嵌哪些领域知识或最佳实践？

每个用例写成：**触发 → 步骤 → 结果**。用户说得含糊时，**提出你猜的用例让他确认**，
而不是默默猜。这一步的产物决定了后面每一步。

判断它属于哪一类，因为这决定结构：

1. **文档与产出物制作** —— 内嵌风格指南、模板、质量清单；
2. **流程自动化** —— 带校验关卡的分步流程；
3. **MCP 增强** —— 按顺序编排 MCP 工具调用，并配上领域判断。

### 第 2 步：规划文件夹结构

- **文件夹名只能 kebab-case**（`my-skill` —— 不能有空格、大写、下划线），且应与 frontmatter 的 `name` 一致；
- `SKILL.md` 必须**正好**叫这个名字，大小写敏感（`skill.md` 不会被识别）；
- **技能文件夹里不要放 `README.md`**；
- 正文控制在 5000 词以内；超出的细节挪进 `references/` 并用链接指过去；
- 关键的校验**优先写成脚本而不是散文** —— 代码是确定性的，语言理解不是。

### 第 3 步：写 frontmatter

**frontmatter 是最重要的一部分** —— 只由它决定这个技能会不会被加载。

```yaml
---
name: your-skill-name
description: [它做什么] + [什么时候用，带上用户真会说的原话] + [需要时再加「不要用于」]
---
```

硬性要求：

- `description` **必须同时说清「做什么」和「什么时候用」**；
  **不能留空** —— 缺 description 是**唯一**会让内核**静默丢弃**整个技能的情况
  （文件还在磁盘上，但模型完全看不到它）；
- **建议不超过 1024 字符**（超了内核仍装载，只是记一条 warning —— 但它每轮都占 token）；
- 写上用户真会说的具体说法；相关时提文件类型；
- frontmatter 里**不能出现尖括号 `<` `>`**（它会被注入系统提示）；
- `name` 建议不超过 64 字符，且不能含 `claude` / `anthropic`（保留字）。

**弱**：`description: 帮助处理项目。`
**强**：`description: 管理 Linear 的迭代流程，包括排期、建任务与状态跟踪。当用户提到「迭代」「Linear 任务」，或要求「建工单」时使用。`

#### `disable-model-invocation: true` 在 Oint 里的实际含义

设成 `true` 后，这个技能**不进系统提示的技能索引** —— 也就是模型完全看不到它，
不会主动加载。用户在输入框敲 `/技能名` 仍然能用。

**但要清楚 Oint 与上游的差别**：Oint 的 `/技能名` 只是把 `/技能名 ` 几个字原样发给模型
（不像提示模板会把正文展开）。所以模型看到的是一个它**在自己的技能清单里找不到**的名字 ——
它得自己去读磁盘上的 SKILL.md 才能知道内容。因此：

- **默认不要开这个开关**。模型看不见的技能，它就没法主动提议；
- 真要用（流程很长、会打断、有副作用的操作，时机该由用户掌握），
  **务必在 `description` 与正文里都写明「只在用户明确要求时使用」** ——
  这样即使将来这个开关被去掉，技能的行为也不会跑偏。

全部可选字段（`license`、`compatibility`、`metadata` 等，以及**哪些字段 Oint 其实不解析**）
与更多正反例，见 [references/frontmatter.md](./references/frontmatter.md)。

### 第 4 步：写正文

推荐的结构：

```markdown
# 技能名

## 指令
### 第 1 步：[第一个主要步骤]
确切的命令 / 工具调用，并写明预期输出。

## 示例
用户说 X → 做什么 → 得到什么。

## 疑难
错误 → 原因 → 怎么修。
```

最佳实践：

- **具体、可执行**：给出确切的命令与参数、预期的输出，而不是「校验一下数据」这种氛围词；
- **关键指令放最前面**；必须遵守的规则用 `## 重要` 之类的标题单独拎出来；
- **写上用户真的会撞到的错误处理**；
- **显式引用随包的资源**（「写查询之前，先读 references/ 里的 API 模式那份」）；
- **必须按顺序发生的步骤要编号**，并写明步骤之间的数据依赖。

结构模式（顺序编排、多 MCP 协调、迭代改进、按上下文选工具、领域知识内嵌）
见 [references/patterns.md](./references/patterns.md)。

### 第 5 步：校验

**跑随包的校验脚本**：

```bash
node "<skill-creator 的 location>/scripts/validate_skill.mjs" <技能文件夹路径>
```

实际用的时候，`<location>` 直接从系统提示的技能索引里抄 —— 它就是 `skill-creator` 那一行的
`<location>`，脚本在同一个目录的 `scripts/` 下。例如：

```bash
node "C:/Users/你/.oint/skills/skill-creator/scripts/validate_skill.mjs" "C:/Users/你/.oint/skills/my-skill"
```

它会检查命名、frontmatter 格式与长度、禁止内容、被引用却不存在的文件、正文体积。
**每一条 ERROR 都要修**；WARNING 当成待复核项。成功时输出 `PASS` 且 0 error。

> **为什么是 Node 而不是 Python**：Oint 自己就是 Electron 应用，**Node 必然在**；
> 而 Python 不保证 —— Windows 上 `python3` 常常是 Microsoft Store 的占位 stub，
> 命令存在、执行却返回 9009 且**没有任何输出**（本机实测如此）。
> 技能里写一条跑不通的命令比没有更糟：模型会反复重试同一个错。
> 所以这里只有 Node 一份实现，不再维护 Python 版。

> ⚠️ **打包后的应用里，脚本的路径要能被执行**。内置技能住在 `app.asar` 归档里，
> 而归档只有 Electron 自己的 fs 补丁认得 —— 模型用 bash 起的 `node` 是独立进程，
> 打开归档内路径一律 ENOENT。所以 `electron-builder.yml` 把
> `resources/**` 整个 `asarUnpack` 拆了出来，`resolveBuiltinSkillDir()` 返回的
> 就是解包后的真实路径。**技能索引里的 `<location>` 因此是外部进程能用的路径**，
> 直接拿它拼 `scripts/...` 即可。要给**用户自己的技能**做校验不受影响。
> 另外 Oint 本身有一条测试在守「SKILL.md 里的相对链接都真实存在」，
> 并且**真的会执行这个脚本一次** —— 那是同类检查的自动化版本。

### 第 6 步：测试与迭代

**在一件难的任务上反复迭代到成功，再把赢的做法提炼进技能** ——
这比广泛测试信号快得多。然后再覆盖：

1. **触发**：明显的说法能加载、换个说法也能加载、不相关的问题不加载；
2. **功能**：输出正确、工具调用成功、边界情况有处理；
3. **与基线对比**：比不用技能时更少的纠正 / 工具调用 / token。

调试技巧：直接问智能体「你什么时候会用 [技能名] 这个技能？」——
它会用自己的话把 description 复述回来，**它漏掉的正是你该补的**。

完整的测试用例模板与迭代信号见 [references/testing.md](./references/testing.md)。

## 工作流：评审一个已有技能

被要求评审或改进技能时：

1. 读它的 SKILL.md，并跑 `node scripts/validate_skill.mjs <文件夹>`（路径见第 5 步）；
2. 对照常见失败模式诊断：
   - **从不触发** → description 太泛，或缺用户真会说的触发词。用原话与关键词重写；
   - **触发太频繁** → 加否定触发（「不要用于…」）并收窄范围；
   - **加载了但指令被忽略** → 指令太长、被埋住、或有歧义。关键规则提到最前，
     散文式的校验换成脚本；
   - **响应变慢 / 变差** → SKILL.md 太大；细节挪进 `references/`；
3. **给出具体改法**（description 的前后对照），而不是泛泛的建议；
4. 用户带来真实会话里的失败例子时，**把修法直接写进技能** ——
   一条明确的指令、一条疑难条目、或一个校验步骤。**这是价值最高的迭代回路。**

## 交付前清单

- [ ] 文件夹是 kebab-case，且与 frontmatter 的 `name` 一致
- [ ] 文件名正好是 `SKILL.md`；文件夹里没有 `README.md`
- [ ] frontmatter 有 `---` 分隔、有 `name`、有「做什么 + 什么时候用」的 `description`，
      且**不超过 1024 字符**（`name` 不超过 64 字符）
- [ ] frontmatter 里没有尖括号
- [ ] 指令具体可执行，带示例与错误处理
- [ ] 每个被引用的 `scripts/` `references/` `assets/` 文件**真的存在**
- [ ] 校验脚本 0 error（或已按上面的清单人工核对）
- [ ] 触发测过：目标说法会加载，不相关的不会
