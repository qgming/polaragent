# 验证规划（Verification Planning）

在改一个非平凡的系统之前，先建立一条**证据路径**：从你要下的那个结论，到能证实它、限定它、或推翻它的证据之间，一条属于**这个项目**的具体路线。

要点不是「挑一个熟悉的验证手法」，而是决定**这个系统怎么才能揭示这次改动的真相**。

## 1. 先把结论说清楚（Frame the claim）

写明：什么行为需要变成真的，以及**在什么条件下你的自信结论会是错的**。

想一想：什么东西必须改、什么东西必须保持不变、行为在哪里跨越了边界、哪一种失败最要紧。

**这一步做完的标志**：结论、它真正的不确定性、以及它的重要失败模式都具体到可以着手查了。

## 2. 设计证据路径（Design the evidence path）

从系统本身推导可能的证据路径：它有哪些**可控输入**、**可观察效果**、**状态迁移**、**不变量**、**边界**、**产物**，以及能不能重放或反转一个场景。

**先产生几个备选再选**。优先选那条「结论可信、代价与风险相称」的路。如果现有系统让关键真相太间接、太含糊，就补一个最小的**验证支点**（能直接读写那个状态、能重复、能定位失败的最小能力）—— 但要把它当成证据路径的一部分，而不是自动变成产品功能。

**这一步做完的标志**：有了一条首选路径、它已知的局限、以及在情况变化时可以退回去的更弱/更强的备选。

## 3. 定验证预算（Set a verification budget）

在最终状态上：列出**彼此独立的结论**，每条指定一个负责人，然后选**最少的、不重复的**证据覆盖这些结论与重要边界。

**证据只在它的代码、输入、环境与状态都还有效时才可以复用。** 仓库与发布要求的检查照做；只有当某个写明了的条件成立时，才扩大或重复验证。

## 4. 路径不明时先调研（Research when the path is unknown）

当正确的证据路径取决于一个你不熟悉的依赖、框架、外部服务或快速变化的能力时，**先派 explorer 做一次聚焦调研**再定方案。要问的是：影响这个具体验证问题的官方设施、约束与取舍。

项目里已有的证据能直接定案的，就用现成的，不要为了调研而调研。

## 5. 让路径可执行（Make the path runnable）

只准备「可靠地走完这条路径」所需要的支持，保持它**窄、可重复、可安全查看**。

想清楚这份支持是有长期价值，还是只为解决当前的不确定性而存在：有长期价值的刻意留下，一次性的用完就删。

**引入依赖、常驻的诊断界面、或纯为取证而做的结构性改动之前，先问用户。**

## 6. 收口（Close the evidence path）

实现之后再走一遍这条路，把得到的证据对着最初的结论解读。

报告这条结论是**被证实了、被限定了、还是被推翻了**；把「已知事实」与「仍然不确定的部分」分开写。

**这一步做完的标志**：后来的读者能看清「结论是靠什么支撑的」以及「它管不到哪里」。

## 尺度（Scope）

**按比例使用这个技能。** 小的机械改动直接走项目常规检查即可；只有更大、多阶段的工作才需要在这里建立证据路径，让后续工作沿着它走。
