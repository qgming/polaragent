---
description: 根据改动生成 PR 描述：背景、改动、测试计划、风险与回滚
---

为当前分支的改动写一份 PR 描述。**只写，不要提交、不要推送。**

## 先收集

`git status`、`git diff <基线分支>...HEAD`（基线从仓库默认分支判断，如 `main` / `master`）、`git log <基线分支>..HEAD --oneline`。改动大时按模块分组看，别漏掉新增文件。

## 输出格式

```
## 标题
<一句话，说清这次改动的结果，而不是过程>

## 背景
为什么做这件事：原来的问题 / 需求来源（一两段；不要写"按照要求修改"这种空话）

## 改了什么
按模块列要点（人能看懂的话，不要逐文件罗列）

## 测试计划
- 怎么验证：具体命令 / 手工步骤
- 已验证：真实跑过的，贴结果
- 未验证：没跑的、需要 reviewer 帮忙确认的（不要含糊过去）

## 风险与回滚
影响面（数据 / 接口 / 兼容性 / 性能）、出问题怎么退回

## Reviewer 关注点
最值得看的 2–3 处，以及你不确定、希望被挑战的地方
```

## 硬约束

- **不许虚构测试结果**：没跑过的写"未验证"，跑过但失败的如实说。
- 改动里夹带无关内容（格式化、误提交、调试代码）要指出来，并建议拆成单独提交。
- 破坏性变更（接口 / 数据格式 / 配置）单独一段写清楚，附迁移方式。
