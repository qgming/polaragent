---
description: 系统化根因排查：复现 → 最小化 → 假设 → 验证 → 修根因 → 补回归测试
---

排查下面这个 bug。**不许猜着改代码** —— 每一步都要有证据。

## 1. 复现

给出**确切的复现方式**（命令 / 输入 / 步骤）与真实的错误输出。复现不了就先说清"我复现不了、缺什么信息"，然后停下问我 —— 不要凭想象去修。

## 2. 最小化

把复现缩到最小：哪个输入、哪个分支、从哪一行开始偏离预期。二分（注释掉一半 / `git bisect` / 打日志）都行，说清你用的是哪种。

## 3. 假设与验证

列出 2–3 个可能的原因，**按可能性排序**，逐个用证据验证（日志、断言、最小实验）。**被推翻的假设也要写出来** —— 那是我判断你思路的依据。

## 4. 修根因

- 修**原因**，不是症状：不要加 `try/catch` 吞异常、不要靠重试掩盖、不要把报错降级成一行日志、不要 skip 掉失败的测试。
- 说清"为什么这处改动就是根因"，而不是"改完不报了"。
- 只改必要的地方；顺带发现的坏味道记下来，不要顺手改。

## 5. 收尾

- 加一个**回归测试**：这个 bug 再出现时必须变红（说明它现在通过、以及为什么它能拦住复发）。
- 搜一下同类问题在别处是否也存在（同一模式的其他调用点）。
- 汇报：根因、证据链、改动、回归测试、同类风险点。

**三次尝试后仍无进展就停下汇报**：已经确认了什么、排除了什么、还缺什么信息。
